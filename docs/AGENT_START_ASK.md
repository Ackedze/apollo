# Старт агента: раздел «Спросить» в Apollo

Это инструкция для разработчика, который дорабатывает чат Apollo вместе с Proxy.
Дизайнеру сначала пройти [общую инструкцию старта](DESIGNER_START.md).
Установку готового Proxy выполняйте по
[инструкции поставки](https://github.com/Ackedze/apollo-proxy/blob/main/macos-app/DELEGATION.md).
Владелец обоих проектов и окончательный ревьюер — **@Ackedze**.

Первая переносимая поставка включает проверку, «Спросить» и Figma MCP.
По решению владельца от 20.10.2026 переносимость frontend с собственным SDK —
следующий этап. Пакет не содержит исходников `arui-private`; frontend в этом
профиле явно недоступен. Это не задача первого PR по чату.

## Первое поручение

Доработать «Спросить»: читаемость чата, ответы под разные вопросы, Markdown,
корректные ссылки на источники и понятные состояния запроса. Сначала изучить
существующий путь запроса от UI до ответа Proxy и выбрать небольшой законченный
сценарий для первого PR. Связанные изменения Proxy и Apollo оформлять двумя PR
с взаимными ссылками и одним описанием пользовательского результата.

Видимые изменения сохраняют идентичность существующего Apollo. Для улучшения UI
использовать проектную дизайн-систему и подходящий UI skill, если он доступен.
Небольшое исправление ссылок не требует переделывать оболочку плагина.

## Источники и границы

- [Apollo](https://github.com/Ackedze/apollo) — Figma plugin, UI и shared runtime.
- [Apollo Proxy](https://github.com/Ackedze/apollo-proxy) — локальный HTTP-сервис,
  выбранный CLI-агент, данные и доставка обновлений.
- [design-system_ab](https://github.com/Ackedze/design-system_ab) — контракты и
  факты компонентов. Рабочие данные потребитель получает из версии поставки Proxy.

Использовать переданные владельцем ветку/commit и выпуск данных. До начала работы
записать `git rev-parse HEAD` обоих репозиториев, версии `package.json`, dataId и
runtime profile из принятой поставки. Если исходники ещё не опубликованы,
попросить конкретный доступный ref или исходный архив; не заменять его старым main.
Пакет данных связан с code runtimeId. Несовместимый пакет не перепривязывать вручную.

Не менять нормы контрактов, audit/capture semantics, генерацию, публикационный ID
плагина, release/version metadata, workflow и секреты в задаче по чату.
Нехватку знания об источнике показывать явно. Не подменять UNKNOWN успешной проверкой.

`arui-private` запрещено push-ить, публиковать копией или включать в поставку.
Обычные проверка макета и «Спросить» не требуют этого репозитория, Figma MCP или SDK.

## Рабочая папка

Выбрать собственную папку. Для существующих cross-repository тестов сохранить
только относительную структуру:

```text
<своя папка>/
  projects/Apollo/
  services/apollo-proxy/
  shared/design-system_ab/   # для полного каталожного integration suite
```

Папка `workplace` и пути автора не нужны. Checkout Apollo и Proxy выполняется
через собственный доступ к GitHub. В каждом репозитории создать свою ветку от
согласованного ref; не сбрасывать незакоммиченные изменения другого участника.

Нужны Node.js 22 и npm. Внутри Apollo:

```bash
npm ci
npm run validate
```

Обычный build сам собирает внутренние Core, generation-core, adapters и pattern-core. Он работает без
соседних каталогов и готового `dist`. Авторская native-диагностика включается
отдельно через явные настройки; для чата её включать не нужно.

Внутри Proxy:

```bash
npm ci
node --test test/dialogue-source.test.js test/dialogue-runtime.test.js test/cli-agent.test.js
```

Эти проверки используют собственные fixtures и fake CLI. Реальный вход и платные
вызовы для них не требуются. `npm start` использует личный вход пользователя
и установленную базу знаний; никогда не копировать чужой `.env` или CLI credentials.

Для ручного теста можно использовать установленное приложение Proxy из принятой
поставки, а локально менять только Apollo. Если меняется Proxy, запускать свою
сборку с собственным портом и конфигурацией данных. До запуска проверить, кому
принадлежит занятый порт. Не завершать чужой процесс; активный запрос дождаться.
UI должен обращаться к фактически выбранному локальному endpoint.
В текущем клиенте `http://localhost:3001` задан в `src/ui.js`: для параллельного
Proxy на другом порту нужен соответствующий dev-клиент. Переключателя endpoint
в настройках плагина сейчас нет.

Пример запуска изменённого Proxy с отдельным dev-state и **начальными данными
совместимой установленной поставки**, из checkout `services/apollo-proxy`:

```bash
APOLLO_USER_PROXY="$HOME/Library/Application Support/ApolloProxyControl/proxy"
APOLLO_STATE_ROOT="$HOME/.apollo-dev/ask-links" \
APOLLO_CLI_PROVIDER=codex \
PORT=3001 \
node scripts/git-data-cli.js run \
  --store "$HOME/.apollo-dev/ask-links/data-releases" \
  --seed "$APOLLO_USER_PROXY/runtime/seed" \
  --runtime "$APOLLO_USER_PROXY/runtime/apollo"
```

Сначала остановить свой миниапп через «Выйти» и убедиться, что порт свободен.
Команда запускает `server.js` из **текущего checkout**, используя неизменяемый
runtime/seed принятой поставки; создаваемый dev-state отделён от состояния
приложения. Это начальный snapshot, а не текущие обновлённые данные миниаппа:
зафиксировать полученный dataId. Не переносить в пример личный `.env`; если в
checkout он уже есть, проверить его настройки и явные переопределения корней.
Для чата с Claude заменить provider на `claude` и использовать свой CLI-вход.
При изменении общего runtime этот пример уже не доказывает совместимость:
нужна соответствующая принятой версии сборка runtime и данных.
После теста завершить dev-сервер Ctrl+C и вернуть свой обычный Proxy.

## Текущий путь запроса

Текущий UI использует `source: codex` как существующее имя локальной ветки API.
Она запускает выбранный в Proxy CLI — Codex или Claude. Прежняя скрытая настройка
Langflow при восстановлении переводится в локальную ветку; это не меняет источник
старых сообщений. Явный Langflow API сохранён для других клиентов.

| Область | Файлы |
| --- | --- |
| React UI и состояния чата | `src/design-check/index.tsx`, controller/state рядом |
| Запрос, источник, история, ошибки | `src/design-check/dialogue-port.js` |
| Markdown и inline-ссылки | `src/design-check/markdown.js`, `markdown-inline.js` |
| HTTP и запуск ответа | Proxy `server.js`: `/analyze`, `callCodexDialogue` |
| Промпт и нормализация истории | Proxy `src/reports/messages.js` |
| Выбранный CLI и диагностика процесса | Proxy `src/cli-agent.js`, `src/config.js` |

Фактический wire contract уже реализован в `createExistingDialoguePort`:

1. UI отправляет `POST /analyze` с `source`, `session_id`, `dialogue` и `text`.
2. `text` содержит JSON-envelope `schemaVersion: 1`, `mode: design-dialogue`,
   вопрос и пустые ссылки на audit context.
3. Proxy возвращает `success`, текст `result` и, при наличии, `source` и
   `knowledgeRelease`. UI проверяет источник и непустой результат.

Сейчас вопрос и история передаются агенту, а выделение, finding и audit report
этот API не передаёт. Передачу контекста проверки нельзя добавить молча в UI.
Отмена в текущем порту имеет `cancelScope: client-only`: поздний ответ не должен
перезаписывать новый чат; обещать остановку серверного процесса без реализации нельзя.

Известный кандидат для первого исправления: промпт Proxy допускает относительный
путь к документу как источник, а UI открывает HTTP(S)-ссылки. Сначала воспроизвести
это на fixture. Определить согласованный формат доступного источника и обработку
недоступной ссылки. Не превращать относительный путь в выдуманный публичный URL,
не открывать произвольные `file:`, `javascript:` и HTML из ответа модели.

## Проверки изменения

Переиспользовать существующие тесты:

- Apollo: `tests/design-check/dialogue-port.test.js`, `inline-chat.test.js`,
  `markdown.test.js`.
- Proxy: `test/dialogue-source.test.js`, `dialogue-runtime.test.js`,
  `cli-agent.test.js`.
- Сборка UI → реальный `/analyze` → fake CLI/provider:
  Apollo `tests/design-check/integrated-ui.browser.cjs`.

Перед PR запустить `npm run validate` Apollo. Для browser fixture нужен
Playwright и собственный Chromium/Chrome. Его можно установить в отдельную
QA-папку и указать `PLAYWRIGHT_MODULE` и `CHROME_PATH`; не добавлять зависимость
в продукт только ради уже существующего тестового скрипта. Пример из Apollo:

```bash
DESIGN_CHECK_QA_ROOT=/absolute/private/qa-output \
PLAYWRIGHT_MODULE=/absolute/qa-tools/node_modules/playwright \
CHROME_PATH=/absolute/path/to/chrome \
node tests/design-check/integrated-ui.browser.cjs
```

`APOLLO_DIALOGUE_TEST_PROXY_ROOT` позволяет явно выбрать checkout Proxy.
Тест создаёт собственные знания и fake CLI, проверяет текущую оболочку 800×860
и окно 1024 px. Он проходит реальный локальный `/analyze`; проверяет Markdown,
безопасные ссылки, отмену, фоновый ответ и сохранение результата проверки.
Вывод браузерного теста сохранять вне публичного source. Для UI проверить
поддерживаемую ширину окна, длинный ответ, прокрутку, фокус клавиатуры, loading,
пустой ответ и ошибку. Скриншоты с реальным макетом не коммитить.

Полный Proxy gate остаётся `npm test`. Он использует каталоги и соседний Apollo,
включая frontend adapter. Сначала выполнить обычный build Apollo, затем из Proxy
запускать полный suite с явными принятыми данными:

```bash
DESIGN_SYSTEM_AB_ROOT=/absolute/accepted/design-system_ab \
DS_AI_HUB_ROOT=/absolute/accepted/knowledge/data/ds-ai-hub \
TMPDIR=/private/tmp npm test
```

В `design-system_ab` нужны также два существующих скрипта migration-artifact
builder/classifier для reproducibility-теста. Потребитель готового Proxy их не
использует. Эти integration inputs выдаются из принятого выпуска/исходников,
а не из личной папки автора. Не обходить отсутствие данных пропуском тестов.
В отчёте отделять self-contained CI чата, полный suite и ручную проверку модели.
Успешный HTTP сам по себе не доказывает успешный ответ модели.

Для первого результата достаточно следующих сценариев:

1. Объяснение компонента с проверяемыми источниками.
2. Сравнение двух компонентов без выдуманных правил.
3. Инструкция по сборке из доступных данных.
4. Недостаточная информация и честное сообщение об этом.
5. Заголовки, списки, таблица, code block, длинный текст.
6. Доступная ссылка, относительный путь и небезопасная ссылка.
7. Ошибка/таймаут/пустой ответ с возможностью повторить вопрос.
8. Новый чат или отмена до позднего ответа прежнего запроса.

## Совместная работа и merge

Один writer на общий source/build root. До сборки выяснить, кто использует его
`dist`; не пересобирать его во время зависимого прогона коллеги. Независимую
работу вести в своём checkout. Не повторять успешные полные suites без изменения
их входов; после релевантных проверок передать конкретный diff и ограничения.

Связанные PR должны сохранять совместимость API, пока обновлена только одна
сторона. Указать порядок merge и пару протестированных commit/dataId. Новое поле
сделать обратно совместимым либо явно согласовать миграцию. Не смешивать первый
чатовый PR с переносом runtime, обновлением контрактов или пакетной генерацией.

@Ackedze остаётся единственным обязательным code owner. После изменений в PR
нужен его approval текущего head commit и успешные обязательные проверки.
Не делать self-merge, не снимать branch protection, не публиковать приложение
или stable data channel. Main хранит принятый код; боевой выпуск выполняется
владельцем после совместной проверки Apollo, Proxy и версии данных.

## Итоговый ответ агента

Указать пользовательский результат, затронутые репозитории и commit/PR, dataId,
выполненные тесты, ручные сценарии и оставшиеся ограничения. Приложить связанные
PR и описание до/после. Указать применение AI и что проверено самостоятельно.
Не объявлять новые генерационные возможности, полноту проверки всех контрактов
или Ready на основании успешного чата.
