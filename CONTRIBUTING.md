# Вклад в Apollo

Apollo принимает внешние исправления и функции через pull request. Этот документ задаёт минимальный контракт для человека и AI-агента, который меняет плагин.

Дизайнеру, который впервые подключается к проекту, начать с
[`docs/DESIGNER_START.md`](docs/DESIGNER_START.md): установка, доступы, собственная
рабочая копия и условия передачи результата.

Для совместной работы над разделом «Спросить» используйте
[`docs/AGENT_START_ASK.md`](docs/AGENT_START_ASK.md): локальная сборка Apollo и
Proxy, фактический API чата, тесты и связанные PR. Окончательное ревью и выпуск
остаётся у @Ackedze; новая роль участника не меняет единственного обязательного
code owner.

## Перед началом

1. Зафиксируйте задачу, ожидаемый результат и границы в Issue или существующем поручении владельца. Для ошибки приложите воспроизводимый сценарий и фактический результат.
2. Для новой функции согласуйте пользовательский сценарий до реализации. Уже выданное поручение не требует повторного согласования или дублирующего Issue.
3. Не включайте в Issue или PR реальные отчёты пользователей, токены, приватные каталоги и внутренние ссылки с закрытыми данными.

Небольшие исправления документации можно отправлять без предварительного Issue.

## Ветки и полномочия

- Владелец и работающие по его прямому поручению агенты используют `main`.
  Внешний участник и его агент работают в собственной ветке от актуального
  `main` и открывают PR обратно в `main`. Без доступа на запись используйте fork.
- Участнику достаточно доступа `Write` для своих веток; `Admin`, чужой аккаунт
  и публикационные секреты для разработки не нужны.
- Окончательное ревью и merge внешнего вклада выполняет **@Ackedze**. Участник
  не делает self-merge, не меняет защиту ветки и не выполняет force push.
- Локальная проверка, merge кода, выпуск Proxy, публикация плагина и активация
  данных — отдельные действия. Вклад через PR не даёт права на выпуск.
- Для совместных изменений Apollo и Proxy нужны связанные PR с проверенной
  парой commit, совместимостью API и порядком обновления. Git объединяет diff,
  но не проверяет совместимость двух программ: её подтверждают тесты и ревью.
- Свой checkout и `dist` принадлежат участнику. Не пересобирайте общую копию,
  используемую чужим прогоном; общий Core/build меняет один назначенный writer.

## Локальный запуск

Требуется Node.js 22 и npm.

```bash
git clone https://github.com/Ackedze/apollo.git projects/Apollo
git clone https://github.com/Ackedze/apollo-proxy.git services/apollo-proxy
cd projects/Apollo
git switch -c contributor/ask-links
npm ci
npm run validate
```

Вместо `contributor/ask-links` выберите своё имя ветки. Для fork замените URL
Apollo своим и сохраните `Ackedze/apollo` как `upstream`. Proxy нужен полному
validate; установка и команды второй стороны описаны в инструкции старта.

Для ручной проверки соберите плагин и импортируйте `manifest.json` через `Figma -> Plugins -> Development -> Import plugin from manifest`.

## Правила реализации

- Один PR решает одну задачу. Не смешивайте рефакторинг, форматирование и изменение поведения без необходимости.
- Исправление ошибки должно содержать regression-тест, который падает без исправления.
- Новая функция должна покрывать основной сценарий и существенные граничные состояния.
- Не добавляйте fallback, скрывающий ошибку reference manifest, component index или contract package.
- Не используйте object spread в main runtime Apollo. Ограничение и пример описаны в `AGENTS.md`.
- Не добавляйте каталоги дизайн-системы в репозиторий Apollo. Данные контрактов
  хранятся в `design-system_ab`; изменение pipeline при необходимости оформляется
  связанными PR в Apollo Proxy и репозитории данных.
- Никаких абсолютных путей автора, зависимости от его `workplace`, установленного
  skill или аккаунта. Используйте конфигурацию, относительные пути проекта и
  синтетические fixtures. Данные и runtime подключаются из согласованной поставки.
- `arui-private` нельзя push-ить, включать в архивы, fixtures или копировать
  в публичные репозитории. Для текущего вклада в чат он не нужен.
- Не меняйте версию плагина, release metadata и публикационные токены. Это делает maintainer перед выпуском.
- После каждого изменения выполняйте сборку. Перед PR обязательно запускайте `npm run validate`.
- Изменение пользовательского поведения должно обновлять `README.md`. Публикационное изменение также обновляет README рабочего пространства.

## Работа с AI

AI-assisted contribution разрешён, но автор полностью отвечает за результат. В PR укажите:

- использованный инструмент или модель;
- какие части были сгенерированы;
- что проверено вручную;
- известные ограничения или непроверенные сценарии.

Не принимаются PR, в которых автор не может объяснить изменение, отсутствуют воспроизводимые доказательства или выполнена широкая несвязанная перезапись кода.

## Подготовка PR

1. Создайте ветку от актуального `main`.
2. Внесите минимальное изменение и тесты.
3. Выполните `npm run validate`.
4. Проверьте плагин в Figma для runtime- или UI-изменений.
5. Заполните PR template полностью и приложите скриншот, видео или тестовый отчёт.
6. Исправьте все замечания и разрешите обсуждения только после фактического исправления.

Уровни риска, требуемые approvals и критерии ревью описаны в [`docs/REVIEW_POLICY.md`](./docs/REVIEW_POLICY.md). Полный набор проверок находится в [`docs/TESTING.md`](./docs/TESTING.md).

## Definition of Done

PR готов к merge, когда:

- scope соответствует зафиксированной задаче или связанному Issue;
- обязательные CI `validate` и `Required approvals` завершены успешно;
- @Ackedze одобрил текущий head commit; после изменений нужен новый approval;
- все обсуждения разрешены;
- тесты и ручная проверка подтверждают заявленное поведение;
- документация обновлена;
- в diff нет секретов, приватных данных, build artifacts и случайных изменений.
