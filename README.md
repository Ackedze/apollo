# Apollo

Основной плагин Figma: [manifest.json](manifest.json), ID публикации **1616850453760090547**. Приложение находится непосредственно в корне репозитория.

[Старт агента](docs/AGENT_START_PROMPT.md) · [Карта проекта](docs/PROJECT_GUIDE.md) · [Старт дизайнеру](docs/DESIGNER_START.md) · [Правила контрибьютинга](CONTRIBUTING.md)

## Что делает Apollo

| Раздел | Возможности |
| --- | --- |
| Дизайн | Собирает факты Figma, проверяет стили/компоненты/контракты, показывает нарушения и покрытие |
| Спросить | Отправляет вопрос и историю выбранному в Proxy агенту |
| Генерация | Планирует ScreenSpec и создаёт Draft через подключённый адаптер; Figma MCP работает без DS-проверки |
| Навыки | Отдельные сценарии, включая предложения по названиям слоёв и выбранные переименования |
| Данные Apollo | Версии контрактов и подключение проверки/Figma/frontend по метаданным Proxy |

Обычная проверка и окно данных не вызывают модель. Агентские действия выполняются
отдельно через Proxy. Проверка компонента и его генерация требуют разных данных
и mapping; текущую поставку сверяйте через API и окно данных. Frontend adapter
есть в коде, но его переносимость с собственным SDK — отдельный этап.

## Быстрый старт разработчика

```sh
npm ci
npm run validate
```

Импортируй корневой manifest в Figma. Сборка создаёт `dist/code.js`, `dist/ui.html` и серверный `dist/runtime.cjs`.
Полный validate использует соседний checkout Proxy; структура всех четырёх
репозиториев и настройки — в [общем старте](docs/AGENT_START_PROMPT.md).

## Код, данные и совместимость

Коллекция ZIP выбирается только её `manifest.json`. При `archivePathBase: "design-system_ab"`
пути указывают на `JSONS/web/components/.../packages` относительно корня DS;
manual/facts выбирает существующий source index. Legacy коллекции и входящие
каталоги ZIP сохраняют прежнюю базу путей. Basename, SHA, canonical source
projection и stale/symlink guards проверяются до использования; history рекурсивно
не подбирается. Дата изменения берётся из `metadata.updatedAt` manual, а точная
версия — из revision и hashes.

- `src/` — проверка макетов, интерфейс и генерация.
- `packages/` — общий ComponentContract Core, планирование и адаптеры.
- `scripts/`, `tests/` — сборка, проверки и инструменты.
- Apollo Proxy расположен в `services/apollo-proxy` workspace и выбирает этот checkout через `APOLLO_PROJECT_ROOT`.
- Контракты и история Proxy хранятся отдельно от кода. Подключение mapping не повышает Draft до Ready.

При проверке контрактов выбранная настройка «Платформа» передаётся как явный
`ViewportClass`, если контракт объявляет такой вход. Она не меняет платформу
захваченного компонента; несовпадение Desktop/MobileWeb остаётся нарушением.
Диагностика свойств зависимостей показывает имя свойства и компонента вместо
служебного пути; исходный trace сохраняется в отчёте.

[Правила переноса и совместимость](MIGRATION.md) · [Архитектурный бэклог](docs/ARCHITECTURE_BACKLOG.md) · [История разработки](docs/DEVELOPMENT_HISTORY.md)

Команды сборки не публикуют плагин и не выполняют push. Текущий интерфейс сохраняет проверки, вопросы и генерацию из прежнего пилота.

«Спросить» использует агента, выбранного в окне «О прокси»: Codex, Claude или корпоративный AlfaGen.
Ответ показывает фактический агент, возвращённый Proxy. AlfaGen использует настроенный HTTP-адрес;
версия его удалённой базы знаний не подменяется версией локального пакета. AI-проверки, навыки и генерация
через AlfaGen пока не поддержаны; для них выберите Codex или Claude.
Старая скрытая настройка чата Langflow автоматически переводится на локальный маршрут
при открытии плагина. История текущего диалога и сессия сохраняются; отдельный
HTTP API Langflow остаётся доступен для клиентов, которые выбирают его явно.

`npm run build` также собирает внутренние Core, Generation Core, оба адаптера и Pattern Core. Обычная
сборка не требует соседних checkout дизайн-системы или `arui-private`.
Версии инструкций генерации хранятся в `skills/` и сверяются с существующим
`skill-profile.json`; личная папка установленных навыков разработчика не нужна.

## Навык «Переназвать слои»

Во вкладке «Навыки» карточка «Переназвать слои» анализирует текущее выделение
через выбранного в Proxy агента и показывает предложения до записи. Основные
изменения выбраны, необязательные выключены. Плагин применяет только выбранные
имена после повторной проверки исходного макета; компоненты, внутренние слои
экземпляров, автоматические имена текста, известные порты/экспорты и закрытые
области защищены. Максимум одного анализа —3000 наблюдаемых узлов и300
доступных кандидатов; для большей области нужно уменьшить выделение.
Последнее проверенное переименование можно вернуть в той же сессии плагина,
если макет с тех пор не изменился. План и результат
хранятся в памяти сессии. Версия правил и общего протокола закреплена отдельно
в `skills/figma-layer-name-hygiene/profile.json`, независимо от профиля генерации.
Анализ начинается с компактного обзора: иерархии кандидатов, имён и общего
словаря текстов. Агент может сразу вернуть план или запросить подробности
до 24 доступных слоёв за шаг. Native bridge читает их только из исходного
выделения и повторно проверяет снимок; произвольный код агента не выполняется.
Proxy ограничивает весь запуск 15 минутами и восемью шагами, включая ожидание
данных плагина. Отмена передаётся Proxy и завершает активный CLI; при потере
соединения серверный бюджет остаётся защитой от бесконечного запуска.
Новый wire-протокол 0.2.0 закреплён отдельно в `run-protocol.js`, старый
протокол и portable runtime не меняются. Правила цикла хранятся на стороне
Proxy и могут обновляться Markdown/profile-пакетом данных с совместимыми pins.
Верхний таб «Навыки» расположен после «Спросить». Карточка открывает окно навыка поверх каталога. Анализ запускается отдельной
кнопкой «Проверить названия» после выбора области; «Остановить» отменяет ожидание
и возвращает окно к запуску. Закрытие крестиком или Escape сохраняет предложения,
выбранные изменения, результат и текущий анализ. Повторное открытие карточки
не запускает новый запрос: для этого есть отдельное действие «Новая проверка».
Предложения показаны таблицей «Было / Стало / Почему»: флажок выбирает изменение,
флажок в заголовке выбирает или снимает все предложения, включая необязательные,
и показывает частичный выбор. Необязательные предложения исходно выключены.
Нажатие прежнего имени показывает слой в Figma. Таблица прокручивается отдельно,
действия остаются у нижнего края окна. Применение и возврат имён используют
прежние проверки актуальности и результат native bridge. Во время выполнения
по центру показаны существующий маскот и одна короткая строка текущей стадии:
чтение слоёв, подбор названий, уточнение содержимого, проверка предложений,
применение или возврат имён. Подробные счётчики запуска сохранены в доступном
статусе для скринридера. Кнопки экспорта отчёта в навыке нет.
«Дизайн» и «Навыки» используют один `AuditMascot`. Во время проверки общий
CSS-цикл на 5,6 секунды двигает взгляд, моргает и слегка увеличивает круг.
Cursor/rAF на это время отключены; после проверки слежение за курсором
возвращается. Цвета качества сохранены, скрытая область приостанавливает цикл,
а настройка reduced motion убирает анимацию. Внутри цикла меняется только
`transform`; плавность в занятом Figma renderer требует отдельного прогона.
`node --test tests/design-check/layer-names-panel.test.js` проверяет переходы,
выбор предложений и действия окна без браузера, Proxy и запуска агента.
`npm run test:skills-ui` проверяет собранный UI, native bridge и HTTP endpoint
на собственных тестовых данных; задайте `DESIGN_CHECK_QA_ROOT`,
`PLAYWRIGHT_MODULE`, `APOLLO_PROXY_TEST_ROOT` для отдельного checkout Proxy
и при необходимости `CHROME_PATH`.

## Проверки и диагностика

Для cross-repository release-тестов полного `npm run validate` нужен checkout
Proxy по структуре из [инструкции разработчику](docs/AGENT_START_PROMPT.md).
Read-only native diagnostics включаются отдельно через `APOLLO_NATIVE_DIAGNOSTICS=1`;
для этого режима явно задаются `APOLLO_CODE_CONNECT_REPO` и
`APOLLO_CONTRACT_CATALOG_PATH` (абсолютные пути или пути относительно Apollo).
Без opt-in диагностический инструмент сообщает, что его входы недоступны;
обычная проверка, чат и генерация используют свои штатные подключения.

### Native nested instance replacement

Core0.1.23 supports the explicit `instanceReplacementDomain` opt-in for a root-owned native instance; the Editor0.2.108 authoring format is unchanged. Family/VARIANT domains remain predicates; missing source proof stays UNKNOWN. A foreign component body does not inherit the parent baseline. The Editor preserves imported replacement domains during rule edits. This support does not grant library membership, generation acceptance or runtime installation.

Apollo's runtime profile accepts version 1 of this feature and validates its binding descriptors through the same Core validator used during evaluation. Unsupported versions and malformed or unversioned descriptors are rejected before loading a contract.

An explicitly scoped replacement becomes inactive only when the published variant, captured root and reference prove the selector value. A variant without that opt-in keeps its ordinary baseline checks; an editable value or missing binding alone never establishes inactivity.

### Навык: последовательные пачки и диагностика

Большая выделенная область читается порциями и разбивается на последовательные
пачки: до 40 кандидатов и 60 000 UTF-8 байт контекста на пачку. Это целевые
размеры запросов, а не гарантия времени ответа модели. Верхняя граница области —
50 000 наблюдаемых слоёв. Прогресс показывает подготовку и завершённые пачки;
после остановки можно продолжить незавершённую пачку без повторного анализа
завершённых. Результаты сохраняются в памяти до закрытия плагина. Изменение
правил навыка между пачками требует новой проверки.

Внутренние слои INSTANCE и определения COMPONENT/COMPONENT_SET защищены от
переименования. Видимый текст экземпляра читается только как контекст.
Предложения применяются после полного анализа и выбора пользователя. Перед
действием все сохранённые факты повторно сверяются синхронно; событие nodechange
само по себе не доказывает актуальность. Проверка после записи сверяет факты,
поэтому отложенное событие собственного переименования не отключает откат.
Общая подписка documentchange и загрузка всех страниц не используются.
Граница 50 000 не является подтверждённым native-бенчмарком: большой финальный
синхронный проход может задержать интерфейс.

В подробностях запуска показаны стадия, время, provider, запрошенная модель
и безопасные события. Запрошенная модель не доказывает, какая модель исполнила
запрос. Старый Proxy без диагностики совместим; сырые ответы, тексты макета,
промпты, пути и credentials в диагностические события не включаются.
AlfaGen для этого навыка не поддержан: выберите Codex или Claude в «О прокси».


## ReGlyph в разделе «Навыки»

«Обновить иконки» выполняет ReGlyph локально, без ИИ и Proxy. Навык доступен
при выборе iOS или Android (АБМ); обе платформы используют одну исходную
матрицу. Для Desktop и MobileWeb правила пока не подключены. Сценарии
«Базовая замена» и «Замена в сервисах» сохранены: проверка выделения, ручной
выбор соответствий, превью и применение после подтверждения. Защищённые
иконки и нативные исключения сохраняются. Изменение платформы или канала
сбрасывает план. Источник и состав переноса: `src/skills/reglyph/ORIGIN.md`.

## Проверка ProgressBar Goal / Limit

В существующем Apollo доступен маршрут «Дизайн → Паттерны → Проверить ProgressBar».
Он проверяет смысловой выбор Goal / Limit через текущий Apollo Proxy на localhost:3001.
После обычной проверки выделенной области используются её наблюдаемые факты и один
ленивый снимок PNG; проверка актуальности макета сохраняется. Агентский результат
показан отдельно от детерминированных нарушений. Этот пилот проверяет только два
правила выбора Goal / Limit и не означает подключения остальных паттернов.


### Выбор платформы в шапке

Desktop, MobileWeb, iOS и Android выбираются в шапке рядом с настройками. Список сгруппирован по Web и ABM; кнопка показывает название и иконку выбранной платформы. Выбор b2b / b2c / site / invest остаётся в настройках. На узком окне навигация занимает отдельную строку.

### Работа с результатом ReGlyph

Проверка закрепляется за исходной областью. Можно выделять другие объекты и
продолжать выбирать, просматривать и применять замены для ранее проверенного
фрейма. Его имя показано в результате. Перед применением плагин проверяет
актуальность исходных иконок и их принадлежность этой области. Новая проверка
использует текущее выделение; смена канала, платформы или сценария сбрасывает план.


### Семантические паттерны: Goal / Limit, Amount и кнопки

В разделе «Дизайн → Паттерны» явный запуск проверяет смысловое применение
ProgressBar Goal / Limit, Amount, Button и IconButton по выделенной области
и подключённым нормам. Для контекстных правил выбирайте блок вместе с
подписями или таблицей. Каждый компонент получает только свои правила;
вложенные служебные части не создают повторных карточек.

UI использует `component-patterns-v2` и требует совместимого кода Apollo Proxy.
Обновление только набора данных код Proxy не обновляет. При старом Proxy
проверка останавливается до агентского запуска с предложением обновить код.
Семантические результаты остаются отдельными от детерминированных нарушений.
Недостаточность контекста не означает соответствие; после изменения макета
предыдущий отчёт помечается устаревшим и переход к объекту недоступен.

### Статистика проверок и навыков

Меню Proxy «Статистика» сохраняет прежнюю историю журнала токенов. Локальные
проверки/перепроверки, проверка и замена ReGlyph, применение и отмена названий
оставляют записи с нулевым расходом. Итоги агентского анализа слоёв и паттернов
не добавляют повторно токены отдельных обращений к модели. Метаданные операций
сохраняются в ограниченной очереди Figma и удаляются после точного подтверждения
Proxy. Сохранение, отправка и повторы работают автоматически, включая восстановление
связи после перезапуска. Служебные сообщения и кнопки обслуживания очереди не
показываются на проверке и в навыках; техническое состояние остаётся в диагностике.
Это локальный журнал операций. Отчёты о результатах проверок передаются отдельным
маршрутом, описанным ниже. Запись статистики
не меняет вердикты и не блокирует работу; аварийно незавершённые локальные
операции не объявляются завершёнными по одному перезапуску Proxy.


### Выдача результатов и каталог действий

Нативная проверка выбранной области публикует результат до загрузки каталога вариантов привязки стилей. Каталог и действия подгружаются отдельно; недоступный Proxy не отменяет готовые результаты. Поздние варианты проверяют актуальность исходного запуска и не заменяют действия более нового запроса. При настоящем прерывании чтения сохраняются доступные факты и отметка неполного покрытия; UI показывает одно пояснение без дублирования предупреждений.

При повторном запуске прежние контрактные и нативные результаты остаются видны
до готовности замены. Действия по устаревшим результатам заблокированы. Неполное
покрытие объясняется по конкретным разделам в раскрываемом блоке, включая различие
между недоступными данными и ещё не подключёнными дополнительными правилами.

Уведомление Figma `nodechange` само по себе не означает изменение макета.
Перед первым асинхронным чтением библиотечных источников проверка фиксирует
свойства и состав области; уведомления сверяются с этим состоянием. Наблюдатель
предыдущего запуска закрывается. Фактические изменения свойств, структуры или
контекста по-прежнему останавливают захват; финальная сверка сохраняется.


### Автоматическая статистика результатов

Контрактная проверка, нативные проверки и анализ паттернов создают компактные
отчёты `apollo-audit-metrics` schemaVersion=2 из уже готовых результатов.
Сохраняются происхождение, run/report ID, связь перепроверки с прежним отчётом,
версии, длительность, classifications, UNKNOWN, покрытие и доступные счётчики
компонентов. Отсутствующие сведения обозначаются null, а не нулями. Полные
snapshots, тексты макета, имена файлов и credentials в этот формат не входят.
Анализ паттернов остаётся отдельным агентским источником.

Сначала отчёт записывается отдельным ключом clientStorage; затем автоматически
передаётся в `POST /statistics/results` Proxy. Только точное подтверждение ID и
SHA256 разрешает удалить копию в плагине. `proxy-durable` означает принятую
локальную ответственность Proxy; это ещё не подтверждение GitHub. После него
Proxy сохраняет очередь до окончательного receipt серверного publisher.
Offline, перезапуск и неверное подтверждение не превращаются в ошибку аудита.
Невалидная запись не блокирует остальные; технические ошибки остаются в логах.

Резерв плагина ограничен 1 MiB/256 записями; отдельный отчёт — 128 KiB.
Переполнение и отказ storage диагностируются; неуспевшие сохраниться записи
повторяются из памяти, её предел также фиксируется в логах. Нельзя гарантировать
сохранение несохранённой записи после аварийного закрытия при заполненном storage.
