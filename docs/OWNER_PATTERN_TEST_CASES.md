# Ручная приёмка паттернов Apollo

Порядок: **проверить свежий UI Apollo и подключение → обязательный smoke → остальные одиночные кейсы → перекрёстные сценарии**. Проверяем смысл применения Goal / Limit, Amount, Button и IconButton. Проверки контрактов и ReGlyph в эту инструкцию не входят.

Ожидания ниже — критерии приёмки, а не уже полученные ответы модели. Автоматические проверки кода прошли; живой прогон новых кейсов выполняет владелец.

## 1. Перед началом

**Совместимые Proxy и данные установлены.** На 29.10.2026 владелец подтвердил успешное повторное обновление; запущенный bundle проверен: **Proxy 1.4.4 / build 2026102901**, данные **`764eee…` / 41 контракт**. Для этих кейсов доставленной сборки достаточно. Сборка **2026102902** с исправлением загрузки остаётся локальной и не является предусловием прогона. Свежесть UI плагина и результаты самих Figma/model-кейсов ещё нужно проверить.

Повторный запрос **пароля macOS** в системном окне Keychain относился к связке ключей. Это не повторная корпоративная активация Apollo: запись активации от 28.10 сохранена.

Теперь проверь свежесть плагина и подключение по шагам ниже, затем начинай smoke. Успешная установка обновлений сама по себе не означает прохождение тест-кейсов.

1. Закрой ранее открытый Apollo в Figma и запусти его заново через **Plugins → Development → Apollo**. Обновление Proxy и знаний само по себе не перезагружает окно плагина.
2. Если подключена другая копия, выбери **Plugins → Development → Import plugin from manifest…** и через диалог выбора файла укажи `/Users/alexkukhta/Desktop/workplace/projects/Apollo/manifest.json`. Затем снова открой Apollo и проверь строку версии в настройках. Терминал не нужен.
3. В настройках нажми плашку **Proxy**, чтобы проверить подключение. Нужен зелёный индикатор. При красном сначала восстанови подключение.
4. **«Посмотреть данные» → «Обновить список»** должно открывать актуальную таблицу без ошибки чтения. Статусы генерации Figma/Front не являются результатами этого теста паттернов.
5. Для этого прогона выбери **Desktop** в шапке. Используй библиотечные экземпляры: `ProgressBar :: Goal / Limit`, `Amount`, `Button`, `IconButton`. Не отсоединяй их от библиотеки и не заменяй нарисованными копиями.

Если вместо нового экрана виден только **«ProgressBar · Goal / Limit»**, открыт старый UI. Новый экран называется **«Паттерны компонентов»**, кнопка — **«Проверить паттерны»**. Если при подтверждённой установке Proxy 1.4.4 / build 2026102901 появляется предложение обновить его код, зафиксируй сообщение и версии: smoke не пройден. Не меняй тестовый макет и не считай это требованием установить локальную сборку 2026102902.

## 2. Как запускать каждый кейс и читать результат

Для Amount, Button и IconButton уже собрана [область с 13 кейсами в Figma](https://www.figma.com/design/I3MsagXR8Tz2eZcGtIgUk8?node-id=14633-74679). Нормы, RuleID, ожидания и инструкции по выделению находятся снаружи белых проверяемых блоков. Ссылки на отдельные кейсы ниже ведут сразу к нужному фрейму или экземпляру. Выделять весь стенд не нужно. Для изменения примеров используй копии, сохраняя тестовые подписи вне проверяемой области.

К каждому кейсу применяй один порядок; конкретное выделение указано в таблицах:

1. Выдели в Figma **один** указанный фрейм или экземпляр. Для контекстных кейсов включи видимые подписи, заголовок таблицы и нужные строки. Не выделяй весь стенд с соседними тестами.
2. В Apollo открой **«Дизайн» → «Паттерны»**.
3. Нажми **«Проверить паттерны»**; для следующего запуска кнопка называется **«Перепроверить паттерны»**. Нижняя общая кнопка **«Проверить»** не заменяет этот запуск. Пока идёт проверка, не меняй выделение и макет.
4. Дождись **«Агентская проверка завершена.»**. Под отчётом проверь версию знаний: она должна начинаться с `764eee9399ac`.
5. Сравни карточку нужного компонента с ожиданием. Через **ⓘ «Сведения проверки» → «Правила»** посмотри результат конкретного правила. Клик по карточке или **«Показать в макете»** должен фокусировать нужный объект. У полностью неприменимого результата отдельной кнопки ⓘ может не быть.

| Видимый результат | Как его трактовать |
| --- | --- |
| **«Соответствует»**, зелёный | Применимые правила выполнены. Другое правило того же компонента может быть «Неприменимо». |
| **«Нарушение»**, красный | Есть нарушение правила уровня error. |
| **«Замечание»**, жёлтый | Есть нарушение уровня warning. Именно так должен выглядеть неоднозначный IconButton в I02. |
| **«Недостаточно данных»**, жёлтый | Явный UNKNOWN: снимка недостаточно для вывода. Это не успешная проверка и не доказанное нарушение. |
| **«Неприменимо»** | Правило не относится к наблюдаемому случаю. Например, правило подписи для Button без текстовой подписи. Это отличается от отсутствия контекста. |

Сверяй **правило**, а не только цвет общей карточки: у Goal/Limit и Amount проверяется по два правила, у Button и IconButton — по одному. Например, Amount вне таблицы может быть зелёным за денежное назначение, а правило валюты внутри ⓘ будет «Неприменимо».

В I02 подтверждённое нарушение имеет уровень предупреждения, поэтому заголовок карточки — **«Замечание»**, жёлтый. Это не «Недостаточно данных». В A06 ожидаемая общая карточка — **«Соответствует»**: денежное назначение подтверждено, а только правило о валюте в таблице — **«Неприменимо»**. Эти два уровня результата указаны на стенде отдельно. При проверке A06 выделяй внутренний белый блок, оставляя норму и ожидание снаружи.

**Не считать успехом:** «Проверка не завершена», таймаут, ошибка источников, предложение обновить Proxy или сообщение, что поддерживаемые компоненты не найдены в заведомо подготовленном кейсе. Это сбой запуска/подключения, а не UNKNOWN. Общие счётчики нарушений на экране «Дизайн» также не заменяют этот отдельный агентский отчёт.

## 3. Обязательный smoke

Сначала выполни **G01 → R01 → G03 → G04 → A02 → A05 → B02 → I02**. R01 использует уже полученный отчёт G01, новый запрос модели для него не нужен. Если ожидаемый результат не совпал, зафиксируй первый сбой; к перекрёстным сценариям пока не переходи.

Открой ссылку и выдели именно фрейм кейса, а не только внутреннюю шкалу. Все запускаются по шагам раздела 2. Полные нормы: **P1/P2** в разделе 7.

**R01 · Устаревший отчёт и фокус.** После G01 нажми «Показать в макете» и проверь фокус на его шкале. Затем выбери другой объект в Figma, не запуская новую проверку. Предыдущий отчёт должен сохраниться с сообщением о необходимости перепроверки; его «Показать в макете» и фокус кликом по карточке должны стать недоступны. Актуальный вид старого отчёта или переход к новому объекту по старой карточке — дефект. После «Перепроверить паттерны» оценивается новое выделение.

## 4. Остальные регрессии

После smoke выполни **G02, A01, A03, A04, A06, A07, B01, B03, I01, I03**. Это вместе со smoke покрывает четыре прежних Goal/Limit и 13 новых одиночных кейсов.

Дополнительно сузь окно Apollo примерно до 400 px: текст карточки должен оставаться читаемым, действия — располагаться под текстом, без горизонтальной прокрутки. Открой ⓘ и закрой через **Escape**; фокус должен вернуться к кнопке сведений. Не путай этот просмотр с новым запросом модели.

## 5. Перекрёстные сценарии — после базовой приёмки

Приступай после успешного smoke и одиночных регрессий на обновлённой паре UI/Proxy. [Область гибридной проверки X01–X05 уже собрана в Figma](https://www.figma.com/design/I3MsagXR8Tz2eZcGtIgUk8?node-id=14641-74678). Полные нормы, RuleID и ожидаемые карточки находятся снаружи белых проверяемых фреймов. По ссылке на отдельный кейс **один раз выдели весь его внутренний фрейм**, затем нажми «Проверить паттерны» / «Перепроверить паттерны». Внешнюю карточку с ожиданием и весь стенд не выделяй.

Прямые ссылки на проверяемые области: [X01](https://www.figma.com/design/I3MsagXR8Tz2eZcGtIgUk8?node-id=14641-74695), [X02](https://www.figma.com/design/I3MsagXR8Tz2eZcGtIgUk8?node-id=14641-74793), [X03](https://www.figma.com/design/I3MsagXR8Tz2eZcGtIgUk8?node-id=14641-74875), [X04](https://www.figma.com/design/I3MsagXR8Tz2eZcGtIgUk8?node-id=14641-74954), [X05](https://www.figma.com/design/I3MsagXR8Tz2eZcGtIgUk8?node-id=14641-75017).

В X01–X03 ожидается по три самостоятельных компонента, в X04–X05 — по четыре. Шкалы сохраняют штатную демонстрационную геометрию preset; подписи описывают назначение, без отдельного числового утверждения о доле заполнения. Это проверка выбора паттерна и разделения контекстов.

Amount и кнопки, для которых нужен самостоятельный результат, должны быть отдельными экземплярами рядом со шкалой, а не её внутренними частями. Вложенные служебные части уже проверяемого компонента не создают повторных карточек. Не оценивай успех по общему числу нарушений: сверяй конкретные объекты и правила в ⓘ.

| ID и цель | Подготовка | Ожидаемый видимый результат / дефект |
| --- | --- | --- |
| **X01 · Общая денежная цель** | Goal «Накопления на оборудование», отдельный Amount `30 000,00 ₽` с подписью «Сумма пополнения» и Button «Пополнить». Нормы P1/P2, M1/M2, B1. | Goal, самостоятельный Amount и Button — **«Соответствует»**; у Amount правило таблицы неприменимо. Должны быть различимы результаты всех самостоятельных компонентов. |
| **X02 · Общий кредитный лимит** | Limit «Доступно по кредитному лимиту», отдельный Amount `50 000,00 ₽` с подписью «Доступно по лимиту» и Button «Изменить лимит». Те же нормы. | Limit, Amount и Button — **«Соответствует»**. Нельзя трактовать лимит как накопительную цель. |
| **X03 · Несколько ошибок одновременно** | Три явно отделённых подписанных блока в одном фрейме: кредитный лимит показан через Goal; «Вес посылки, кг» показан через Amount; заявка отправляется Button «Заявка». Нормы P1/P2, M1/M2, B1. | Красные нарушения должны объяснять неверный тип шкалы, неденежный Amount и подпись Button. Одна ошибка не должна скрывать остальные или переносить денежный смысл на блок веса. |
| **X04 · Таблица, кнопка и иконка** | Таблица A05 с повтором ₽, рядом Button «Заявка»; в отдельном видимом пустом блоке — неоднозначный IconButton из I02. Нормы M1/M2, B1, I1. | Повтор валюты и подпись Button — красные **«Нарушение»**; IconButton — жёлтое **«Замечание»**. Для денежных строк M1 остаётся выполненным. Нельзя потерять warning среди красных результатов. |
| **X05 · Не переносить соседний контекст** | В одном выбранном фрейме два отчётливо отделённых блока: Goal «Накопления на оборудование» и Goal с нейтральной подписью «Показатель» без назначения. Рядом — самостоятельный баланс Amount `210 000,06 ₽` и Button «Сохранить». Нормы P1/P2, M1/M2, B1. | Первый Goal, Amount и Button — **«Соответствует»**; второй Goal — **«Недостаточно данных»**. Назначение соседней шкалы/баланса не должно превращать его в уверенный PASS или нарушение. |

Это совместное применение существующих правил. Новые требования к согласованности разных компонентов этим пилотом не добавлены. Все пять сценариев собраны и визуально проверены; их ответы модели ещё нужно получить. В реализованном X05 вместо первоначально запланированного `90%` использована подпись «Показатель»: смысл проверки остаётся тем же — назначение второй шкалы неизвестно, а демонстрационная геометрия библиотеки не меняется.

## 6. Как сообщить результат

Для первого несовпадения достаточно заполнить:

```text
Кейс: A05 / X04 / …
Apollo: версия и сборка из настроек
Proxy: версия из интерфейса; знания: …
Figma: ссылка на проверенный внутренний фрейм
Выделял: весь фрейм / таблицу / только экземпляр …
Ожидал: …
Получил: заголовок карточки, объяснение, результат нужного RuleID из ⓘ
Приложено: скриншот выделения и результата; при необходимости — окно ⓘ
Экспорт отчёта, если уже есть: имя файла / ссылка
```

У этого агентского блока нет отдельной кнопки экспорта отчёта. Не нужно искать её или запускать ещё одну проверку ради файла: достаточно скриншотов и текста сведений. По окончании пришли список пройденных ID и отдельно — несовпадения и ожидаемые UNKNOWN.

## 7. Нормы для подписей кейсов

Короткие обозначения ниже используются только для удобства инструкции. На внешней рамке кейса размещай **полную норму и полный RuleID**, не один код P1/M1.

| Код | Полная норма и RuleID |
| --- | --- |
| **P1** | Используй `ProgressBar :: Goal`, когда шкала показывает продвижение к целевому значению. Goal описывает положительное движение к цели, а не риск или расходование ограничения. **`rule:components.progress-bar.goal-for-target-progress`** |
| **P2** | Используй `ProgressBar :: Limit`, когда шкала показывает лимит, порог, доступный объём, риск превышения или отсутствие лимита. **`rule:components.progress-bar.limit-for-threshold`** |
| **M1** | Amount используется для денежных сумм и балансов. Баллы регулируются отдельным паттерном. Проценты и произвольные величины с единицами не относятся к этому паттерну. **`rule:components.amount.monetary-values-only`** |
| **M2** | Если валюта указана в названии колонки и все суммы в колонке в одной валюте, валюту не дублируют в значениях. **`rule:components.amount.table-currency-not-duplicated`** |
| **B1** | Текст кнопки должен называть действие, которое произойдёт после нажатия. **`rule:controls.buttons-and-button-groups.action-verb`** |
| **I1** | Используй IconButton только там, где смысл действия считывается из контекста без дополнительного пояснения. Уровень нарушения — warning. **`rule:controls.buttons-and-button-groups.icon-button-clear-context`** |
