# Старт работы агента над Apollo и Apollo Proxy

Ты помогаешь участнику команды разрабатывать Apollo и Apollo Proxy. Финальный
ревьюер, принимающий изменения и выпускающий версии, — **@Ackedze**.
Инструкция общая: область работы определяется выданной задачей. Подготовь
окружение, изучи затронутые модули и продолжай порученную работу.

## 1. Подключение четырёх репозиториев

Используй собственную рабочую папку и свой доступ к GitHub. Для новых checkout:

```bash
mkdir -p projects services shared
git clone https://github.com/Ackedze/apollo.git projects/Apollo
git clone https://github.com/Ackedze/apollo-proxy.git services/apollo-proxy
git clone https://github.com/Ackedze/design-system_ab.git shared/design-system_ab
git clone https://github.com/Ackedze/design-system_abm.git shared/design-system_abm
```

| Репозиторий | Назначение |
| --- | --- |
| Apollo | Figma-плагин: интерфейс, сбор фактов, проверки, генерация и навыки |
| Apollo Proxy | Локальный HTTP-сервис, запуск агентов, контрактные данные и обновления |
| design-system_ab | Контракты, факты и данные основной дизайн-системы |
| design-system_abm | Каталоги Figma ABM, reference manifest и индексы компонентов |

Если копии существуют, проверь remote, ветку и рабочее дерево. Не перезаписывай
их, не выполняй reset/clean и не удаляй чужие изменения. При отказе доступа
проверь собственный аккаунт, сохрани точный URL и ошибку. Не подставляй похожий
репозиторий. Продолжай независимые доступные шаги.

Зафиксируй SHA всех четырёх доступных checkout. База — актуальный `origin/main`,
если владелец не передал другой ref. Исходники из Git, установленный Proxy
и опубликованный плагин могут иметь разные версии: проверяй фактическую пару.

## 2. Знакомство с проектом

Прочитай применимые `AGENTS.md`, `README.md` и `CONTRIBUTING.md` обоих проектов.
Затем прочитай:

- Apollo: `docs/PROJECT_GUIDE.md`, `docs/DESIGNER_START.md`, `docs/TESTING.md`,
  `docs/REVIEW_POLICY.md`.
- Proxy: `docs/PROJECT_GUIDE.md`, `macos-app/DELEGATION.md`,
  `docs/git-data-update.md`.
- Репозитории данных: README и инструкции затрагиваемых каталогов.

Карты проекта показывают модули и маршруты. Дальше читай только нужные исходники
и тесты. Не загружай все manuals, каталоги и историю в контекст агента.
Специализированные документы, включая `docs/AGENT_START_ASK.md`, нужны только
для соответствующей задачи.

Различай функции:

- «Дизайн» собирает факты Figma и выполняет детерминированные проверки.
  AI-пояснения и анализ — отдельные действия.
- «Спросить» передаёт вопрос и историю выбранному агенту через Proxy.
- «Генерация» готовит ScreenSpec и использует доступный адаптер/mapping.
  Figma MCP собирает Draft без DS-проверки и сохраняет частичный результат при сбое.
- «Навыки» выполняют отдельные сценарии. Переименование слоёв начинается
  с предложений; выбранные изменения применяет плагин после проверки актуальности.
- «Данные Apollo» читает метаданные подключения из Proxy без запуска агента.

Наличие контракта, mapping или адаптера в коде не доказывает доступность функции
в конкретной поставке. Проверяй runtime, данные и конфигурацию. Переносимость
frontend с собственным SDK остаётся отдельным этапом.

## 3. Ветки и полномочия

Ты внешний контрибьютор: создай свои ветки от согласованной базы в каждом
изменяемом репозитории. Например, для свежих чистых clone:

```bash
git -C projects/Apollo switch -c contributor/first-task
git -C services/apollo-proxy switch -c contributor/first-task
```

Выбери собственное имя. Без доступа Write используй fork, добавь исходный
репозиторий как upstream и направляй PR в исходный `main`. Репозитории данных
читай; меняй их только в рамках поручения. Работа владельца напрямую в `main`
не даёт такого права внешнему участнику.

Не выполняй merge, публикацию плагина, выпуск Proxy, активацию данных,
force push или изменение branch protection. Итоговое решение — у @Ackedze.

## 4. Зависимости, сборка и проверки

Для разработки нужны Git, Node.js 22 и npm; для ручного теста — Figma Desktop
и разрешённый тестовый файл. Установи зависимости по lockfile:

```bash
npm --prefix projects/Apollo ci
npm --prefix services/apollo-proxy ci
npm --prefix projects/Apollo run validate
```

`validate` Apollo включает type-check, build и тесты. Внутренние пакеты собираются
штатным build. Полная проверка использует соседний Proxy: сохраняй структуру выше.
Не подставляй чужой готовый `dist` вместо исходников.

Для Proxy выбирай релевантные тесты из `test/`, затем требуемую интеграцию.
Полный `npm test` требует согласованных данных `design-system_ab`, знаний
`ds-ai-hub` и сборки Apollo. Закрытые знания получай разрешённой поставкой;
не добавляй пятый checkout без необходимости. При отсутствии входов укажи
ограничение; не меняй guards, expected values и skip ради прохождения тестов.

На macOS для тестов Proxy используй `TMPDIR=/private/tmp`. Пример из его корня:

```bash
TMPDIR=/private/tmp node --test test/dialogue-source.test.js test/dialogue-runtime.test.js test/cli-agent.test.js
```

Пример проверяет диалог и CLI, а не весь Proxy. Для своей области используй
команды из карт проекта и test scripts. Разделяй fixtures, реальный вызов модели
и ручную проверку Figma. Не повторяй успешный полный suite без изменения входов
или новой причины.

## 5. Локальный запуск и данные

Используй совместимую поставку Proxy, собственный аккаунт провайдера и свою
конфигурацию. Для dev-сервера следуй карте Proxy и инструкции поставки.
Простое `npm start` не устанавливает runtime и знания; миниапп не начинает
исполнять изменённый checkout автоматически.

Не копируй чужие `.env`, credentials, настройки и историю. Папка `workplace`,
абсолютные пути и установленные skills автора не должны требоваться.
Зафиксируй версии кода, runtime profile, `runtimeId` и `dataId`.

Clone данных не активирует их в Proxy. Установленный сервис использует
совместимую поставку; Git-обновление контрактов и обновление кода — разные
действия. Не редактируй generated indexes вручную и не перепривязывай
несовместимый пакет. Сохраняй данные, историю и авторизацию своей установки.

Перед запуском выясни владельца занятого порта. Не останавливай чужие процессы
и активные запросы. Используй свой dev-state. Endpoint плагина должен совпадать
с dev-сервисом: проверь клиент и `networkAccess` manifest.

Импортируй `projects/Apollo/manifest.json` через Figma → Plugins → Development →
Import plugin from manifest. После пересборки закрой и заново открой плагин.
Проверь `/health`, `/v2/contracts` и окно «Данные Apollo». Успешный HTTP
не доказывает успешный ответ модели или готовность генерации.

Для проверки и диалога Figma MCP не нужен. Для генерации настрой собственные
OAuth, целевой файл и принятый MCP-профиль по инструкции Proxy. У провайдеров
разные возможности; имя маршрута с `codex` не доказывает фактического агента.
Не добавляй скрытый fallback на другую модель или провайдера.

## 6. Реализация и передача

Проследи затронутый путь от UI/native до Proxy и ответа. Найди места вызова,
API, тесты и данные. Решай одну законченную задачу минимальным понятным
изменением, переиспользуя компоненты и зависимости. Для ошибки сохрани
воспроизведение и добавь содержательную регрессию.

Сохраняй cancellation, защиту от поздних ответов, актуальность снимков,
ownership, обработку ошибок и доступность. UNKNOWN не заменяй PASS,
а Draft — Ready. Не расширяй задачу до изменения норм, runtime или генерации,
если это не требуется поручением. Для общего source/build root назначается
один writer; не пересобирай входы, используемые чужим прогоном.

Для UI сохраняй идентичность и дизайн-систему Apollo. Проверь размеры окна,
клавиатуру, прокрутку, loading, пустое состояние, ошибку и отмену.
Не выполняй произвольный HTML/JS ответа модели и не выдумывай источники.

`arui-private` запрещено push-ить или публиковать копией, включать в архивы
и fixtures. Не коммить секреты, реальные отчёты, private-каталоги,
`node_modules`, историю и временные результаты. Публикационный ID и release
metadata не меняй без отдельного поручения владельца.

Подготовь PR для каждого изменённого репозитория. Свяжи PR Apollo/Proxy ссылками,
укажи протестированную пару SHA, `dataId`, совместимость API и порядок обновления.
Промежуточное обновление одной стороны должно сохранять совместимость.
Обязательные checks и ревью @Ackedze должны пройти до merge.

В отчёте укажи репозитории и SHA, ветки, версии и данные, пользовательский
результат, изменённые модули, проверки и ограничения. Приложи diff/PR
и обезличенные результаты до/после; раскрой использование AI. Если поручена
только подготовка, перечисли выполненные подключения, готовые функции
и точные блокеры, не заявляя непроверенное готовым.
