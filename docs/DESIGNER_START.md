# Старт дизайнера в Apollo

Эта инструкция подходит дизайнеру, который тестирует Apollo и дорабатывает его
вместе со своим агентом. Финальный ревьюер и ответственный за выпуск — **@Ackedze**.

## Что получить перед началом

- Задачу с ожидаемым результатом и границами. Первое направление — раздел
  «Спросить»: чат, формат ответов, Markdown, ссылки и состояния запроса.
- Версионный ZIP `ApolloProxyControl-macOS-<build>.zip` и способ запуска
  совместимого Apollo: опубликованный плагин либо исходники для Development.
- Для разработки — доступный ref/commit обоих репозиториев и свои доступы GitHub.
  Обычно база — актуальный `main`. Если нужные изменения ещё не отправлены,
  владелец передаёт доступный ref или архив: старый публичный `main` не считается
  заменой согласованной сборки.
- Подтверждение владельца, что в удалённом `main` обеих сторон есть CODEOWNERS
  и обязательные workflows. Подготовленный локальный файл ещё не защищает PR:
  [состояние подключения Proxy](https://github.com/Ackedze/apollo-proxy/blob/main/CONTRIBUTING.md#pull-request-и-выпуск).
- Версию данных `dataId`, runtime profile и адрес обновлений из этой поставки.
  Встроенные данные работают без отдельного checkout контрактов. Закрытые знания
  передаются разрешённой поставкой, а не коммитом в публичный репозиторий.

Нужны macOS 13+, Figma Desktop и собственный аккаунт агента с доступом к модели.
Для разработки дополнительно нужны Git, Node.js 22 и npm. Готовое приложение
содержит Node; для обычной установки отдельно устанавливать его не требуется.

Первая переносимая поставка включает проверку, «Спросить» и экспериментальную
генерацию Figma MCP на поддержанных mapping. Frontend с собственным SDK — отдельный
этап. `arui-private`, папка `workplace`, аккаунты и установленные skills автора
не требуются.

## 1. Подключить свою установку

1. Установить переданный Proxy по [инструкции приложения](https://github.com/Ackedze/apollo-proxy/blob/main/macos-app/DELEGATION.md).
   Ранее запущенный свой Proxy завершить через меню AP после окончания запроса.
   Если порт 3001 занят неизвестным процессом, сначала выяснить владельца.
2. В AP → «О прокси…» выбрать Codex или Claude и выполнить **собственный вход**.
   Codex можно установить кнопкой приложения; Claude Code устанавливается отдельно.
   Подписки/модель оплачиваются по условиям личного или командного аккаунта.
   Пароли, токены и файлы авторизации никому не передаются.
3. Нажать «Запустить прокси». Диагностика `http://127.0.0.1:3001/health`
   должна отвечать, `http://127.0.0.1:3001/v2/contracts` — возвращать установленный
   набор контрактов. HTTP-ответ ещё не доказывает успешный ответ модели.
4. Открыть совместимый Apollo. Для своей сборки: Figma → Plugins → Development →
   Import plugin from manifest → `projects/Apollo/manifest.json`.
   После пересборки закрыть и заново открыть плагин, чтобы не тестировать старый UI.
5. В окне «Данные Apollo» сверить подключение и версии. Проверить тестовый компонент,
   затем задать в «Спросить» вопрос, например «Какие состояния есть у IconView?».
   Сохранить результат и доступность ссылок. UNKNOWN и неполное покрытие не означают PASS.

Для проверки и чата отдельный Figma MCP не нужен. Обычная проверка контрактов
выполняется плагином и Proxy; вопрос и история «Спросить» передаются выбранному
агенту. Текущий чат не передаёт выделение или отчёт проверки автоматически.
Использовать для ручных тестов разрешённый тестовый файл, без конфиденциальных данных.

### Генерация Figma MCP — только если нужна задаче

Текущий генерационный CLI-профиль реализован для **Codex**; поддержка Claude
в чате не означает поддержку генерации через Claude. Нужны собственный доступ
на редактирование целевого Figma-файла и OAuth-подключение Figma в том же CLI-аккаунте,
которым запускается Proxy. Подключение Figma в другом приложении не доказывает
авторизацию CLI.

Подключить официальный endpoint `https://mcp.figma.com/mcp` с именем
`apollo_figma_mcp`, завершить OAuth/Allow access. Затем задать **свой** `fileKey`
командой `configure-portable.js --figma-file` из
[инструкции Proxy](https://github.com/Ackedze/apollo-proxy/blob/main/macos-app/DELEGATION.md#пути-и-команды-для-настройки).
Этот параметр выбирает файл и не выполняет OAuth. Перезапустить свой Proxy после
завершения запросов и проверить небольшой макет в тестовом файле.

По умолчанию MCP собирает Draft без DS-проверки. Частичный результат сохраняется
при сбое; завершение генерации не означает Ready или полное покрытие норм.
Для работы только над «Спросить» этот шаг пропускается.

## 2. Подготовить разработку

Каждый участник использует собственную папку. Для существующих интеграционных
тестов важна только относительная структура:

```text
<своя папка>/
  projects/Apollo/
  services/apollo-proxy/
  shared/design-system_ab/  # только для каталожной интеграции
```

Из новой пустой рабочей папки с доступом на запись в репозитории:

```bash
git clone https://github.com/Ackedze/apollo.git projects/Apollo
git clone https://github.com/Ackedze/apollo-proxy.git services/apollo-proxy
git -C projects/Apollo switch -c designer/ask-links
git -C services/apollo-proxy switch -c designer/ask-links
npm --prefix projects/Apollo ci
npm --prefix services/apollo-proxy ci
npm --prefix projects/Apollo run validate
```

Имя `designer/ask-links` заменить своим. Перед следующей задачей получить свежий
`origin/main` и создать новую ветку от него. Без `Write` использовать forks;
сохранить оригинальные репозитории как `upstream`, PR направлять в их `main`.
При переданном другом ref начать именно с него и указать его в PR.

Тесты чата Proxy выполняются из `services/apollo-proxy`:

```bash
node --test test/dialogue-source.test.js test/dialogue-runtime.test.js test/cli-agent.test.js
```

Они используют fake CLI и синтетические данные, не расходуют запросы модели.
Полный `npm test` Proxy требует согласованных данных и соседнего Apollo:
[входы и команды](AGENT_START_ASK.md#проверки-изменения). Если входы ещё не выданы,
отметить непроверенную интеграцию; не менять guards или пропускать упавшие тесты.
До merge её проверяет maintainer на принятом наборе.

Для UI-доработки достаточно собственной сборки плагина и выданного Proxy.
Для изменения Proxy агент запускает checkout с личной конфигурацией и принятыми
runtime/данными по [инструкции разработчику](AGENT_START_ASK.md#рабочая-папка).
Простое `npm start` без полной базы знаний не является готовой установкой.
Managed-приложение не начинает исполнять изменённый checkout автоматически.
Клиент сейчас использует `http://localhost:3001`; при другом порте нужен
соответствующий dev-клиент. Не запускать два сервера на одном порту и не заменять
код, данные или настройки чужой установки.

## Где хранятся данные

| Что | Где |
| --- | --- |
| Исходники и ветки | Собственные checkout Apollo и Proxy |
| Установленный код Proxy | `~/Library/Application Support/ApolloProxyControl/proxy` |
| Текущие и предыдущие данные | `~/Library/Application Support/ApolloProxyControl/data-releases/` |
| Личные подключения и созданные конфиги | `~/Library/Application Support/ApolloProxyControl/portable-settings.json`, `config/` |
| История диагностики и генерация | `~/Library/Application Support/ApolloProxyControl/history/`, `generation/` |
| История чата плагина | Локальное хранилище Figma-плагина |
| Авторизация агента/Figma MCP | Собственное хранилище официального CLI/OAuth; в Git не попадает |

Proxy получает контрактные обновления из выданного Git/HTTPS-индекса и проверяет
совместимость runtime и hashes. Для этого не нужны Git write-доступ и токен автора.
Обновление данных не обновляет код Proxy или плагина. Текущий Git-канал обновляет
контракты, сохраняя установленную локальную базу знаний:
[как работает обновление](https://github.com/Ackedze/apollo-proxy/blob/main/docs/git-data-update.md).

## 3. Передать результат владельцу

- Дизайнер и его агент работают в собственных ветках. Владелец и его агенты
  работают в `main`; это не разрешение внешнему участнику писать туда напрямую.
- Один PR — один законченный сценарий. Для Apollo + Proxy открыть связанные PR:
  указать проверенную пару commit, dataId, порядок обновления и совместимость
  со старой версией второй стороны. Код и данные не менять одной скрытой подменой.
- Перед PR выполнить проверки затронутой стороны. Для Apollo обязателен
  `npm run validate`; для видимого UI — ручная проверка Figma: длинный ответ,
  ссылки, прокрутка, клавиатура, loading, ошибка, отмена и повторный запрос.
  Приложить обезличенные скриншоты/результаты и назвать непроверенные сценарии.
- Не включать `.env`, историю, реальные отчёты, закрытые знания, SDK и собранные
  приложения. Не менять manifest ID, версии выпуска, защиту веток или stable channel.
- После правок по ревью обновить тесты и запросить новое ревью текущего commit.
  **@Ackedze принимает окончательное решение и выполняет merge и выпуск отдельно.**

Правила обеих сторон: [Apollo](../CONTRIBUTING.md),
[Proxy](https://github.com/Ackedze/apollo-proxy/blob/main/CONTRIBUTING.md).

> укажи commit/dataId, результаты и ограничения. Ничего не мержи и не публикуй.
